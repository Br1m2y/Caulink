# 双源并行实测：叠加成立，1.39×，瓶颈在 AP 不在软件

> 硬件：Intel AX211（`WLAN`，10.6.93.195）+ AIC8800D80 USB（`WLAN 2`，10.6.54.214）
> 网络：校园网 SSID `CAU`，两块网卡均 5 GHz
> 方法：`test/download/dl_two_ip_win_test.go`，20 MiB / 8 分片 / 经 HTTP 代理

---

## 一、结果

| 场景 | 速率 | 说明 |
|---|---:|---|
| 单独 `10.6.93.195` | 5.33 MB/s | 单连接 |
| 单独 `10.6.54.214` | 5.25 MB/s | 单连接 |
| **双源 8 连接** | **7.38 MB/s** | 20 MiB / 2.84 s |
| 对照：两路之和 | 10.58 MB/s | 理论上限 |
| **实际 / 最大单路** | **1.39×** | |
| 实际 / 两路之和 | 0.70× | |

两条链路都真的在干活，不是一条扛全部：

```text
WLAN 2@10.6.54.214   下行  12.56 MiB
WLAN@10.6.93.195     下行   7.55 MiB
调度分配：WLAN 2 × 5，WLAN × 5
```

内容校验：拼接后 md5 与单流下载逐字节一致。

**没到 2 倍的原因很明确**：两块网卡连的是**同一台 AP**。

```text
WLAN    AP BSSID ec:da:59:0e:0c:c0  Channel 44  Signal 80%
WLAN 2  AP BSSID ec:da:59:0e:0c:c0  Channel 44  Signal 96%
```

同一 BSSID、同一信道，空口时间与 AP 上联是共享的。这不是软件的瓶颈，是拓扑。要看到接近 2 倍，必须让两条链路落在不同的 AP（或不同交换机端口）。

## 二、过程中发现两个真问题（比结果本身更重要）

### 1. Windows 双网卡同网段，只绑源 IP 不够 —— 必须 `IP_UNICAST_IF`

两块网卡同在 `10.6.0.0/17`、默认网关都是 `10.6.0.1` 时：

- 只用 `bind()` 绑源地址：包被内核按目的地址选路，从 metric 更低的那块网卡发出，源 IP 却属于另一块 → 接入交换机按源 IP/MAC 不匹配丢弃。
- 实测：绑定 `10.6.54.214` 连续 3 次请求**全部 8 秒超时**，同时 `10.6.93.195` 正常（0.17 s）。
- 反证：把主网卡 WiFi 断开、只剩 USB 网卡时，`10.6.54.214` 立刻恢复正常。

修法是按 socket 设 `IP_UNICAST_IF`（`IPPROTO_IP`，opt 31，**接口索引需网络字节序**）。加上之后：

| | 不加 | 加上 |
|---|---|---|
| 10.6.54.214 首字节到达 | 超时 | 正常 |
| 认证请求 | `context deadline exceeded` / `HOSTUNREACH` | 登录成功 |
| 双源并行下载 | 一条链路扛全部 | 两条各扛一半 |

**这意味着认证层和代理层都要改。** 认证器 `internal/drcom` 与 `internal/proxy/dialer` 当时都只用 `net.Dialer.LocalAddr`，在 Windows 双网卡同网段场景下会直接失效 —— 用户看到的是「第二个 IP 一直认证中」或「第二条线路没速度」。Linux 上没这个问题（内核按源地址反查路由更严格），所以只在 Windows 暴露。

> 该缺陷已修复：`internal/netsrc` 提供 `DialControl`，6 处源地址绑定点全部接上。
> 实现细节、字节序的坑与真机对照见 [`unicast-if.md`](unicast-if.md)。
> 一个容易写错的细节：`IPV6_UNICAST_IF` 的接口索引要**主机序**，与 v4 的 `IP_UNICAST_IF`（网络序）相反，写反会报 `WSAEINVAL`。

### 2. 测试方法本身有坑：keep-alive 会把并行请求串成单连接

第一版测试用默认 `http.Transport` 跑 8 个 Range 请求，结果 20 MiB 全走了一条连接，另外 7 条隧道只搬了 0.01 MiB。表面看是「并行完全无效」，实际是 HTTP/1.1 keep-alive 把 8 个请求复用到同一条隧道上，测的是单连接串行。

第一轮测出的 5.93 MB/s（≈ 单源）就是这么来的，**不作数**。修法是 `DisableKeepAlives: true`，让每个 Range 请求独占一条连接。

顺带发现 Go 的 `Transport` 在某些隧道建连失败时会静默重试，所以最终拨号次数会多于分片数（本次 8 片产生 10 次拨号，其中 2 次是重试）。做统计时按「实际搬运字节」算，不要按「拨号次数」算。

## 三、结论

1. **「多 IP 并行下载不可行」的说法不成立** —— 双源实测跑通，两路都在扛数据，内容正确。
2. **但叠加比不是 IP 数量决定的**，取决于两条链路是否共享上游。同 AP 下只有 1.39 倍。
3. **Windows 上必须补 `IP_UNICAST_IF`**，否则同网段双网卡的产品形态是坏的（认证和代理都会受影响）。已补。
4. 答辩时可以说：机制已验证、两路并行成立；叠加幅度受 AP 拓扑限制，换到不同 AP 可进一步提升。这个说法经得起追问。
