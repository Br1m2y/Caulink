# 多 IP 并行下载：可行性核实与方案取舍

> 起因：有人判断「HTTP 下载在更换 IP 后便会中断，所以无法实现多 IP 并行下载」。
> 本文把这句话拆成两半分别核实：**一半成立，一半不成立，而结论恰好相反。**

---

## 0. 结论

**「单条 TCP 连接不能换源 IP」成立；「所以不能多 IP 并行下载」不成立。**

并行下载从来不是让一条连接换 IP，而是**开多条连接，每条各自固定在一个 IP 上**。这是 IDM、aria2、迅雷的共同做法，也是本项目 Steam 多连接下载已经在跑的机制。

用仓库现有代码（未改一行）实测这条链路：

| 场景 | 数据量 | 墙钟 | 速率 | 对照倍数 | 内容校验 |
|---|---:|---:|---:|---:|---|
| 单连接 · 直连 | 20 MiB | 3.68 s | 5.70 MB/s | — | md5 `347047…f002` |
| 单连接 · HTTP 代理（对照组） | 20 MiB | 3.65 s | 5.74 MB/s | 1.00× | 与直连相同 |
| 4 连接并行 · HTTP 代理 | 20 MiB | 3.72 s | 5.63 MB/s | **0.98×** | 与参照**逐字节相同** |
| 4 连接并行 · SOCKS5 | 20 MiB | 3.54 s | 5.92 MB/s | **1.03×** | 与参照**逐字节相同** |

四片各 5 MiB，拼接后 md5 完全一致 —— 说明 Range 分片经代理链路是正确、可用的，不存在「换 IP 就坏」的协议障碍。

单连接与 4 连接走同一条代理链路，速率基本相等（0.98–1.03 倍）—— 这不是「并行没生效」，而是**限速按 IP 计量**：四条连接在同一个 IP 上分同一份额度。这恰好说明多一个 IP 就多一份额度。

**更重要的一点：** 观察到的「断」，最可能不是并行下载的问题，而是另一个已存在的设计行为 —— **明文 HTTP 路径每条请求都会重新选路**。用两个条目实测，连续 4 次请求的分配是 `A 2 次 / B 2 次`，交替进行。对签名 URL、会话绑 IP 的站点，这确实会表现为「下到一半失败」。这与并行无关，单流也一样会中招。

---

## 1. 三条被证实的事实

### 1.1 连接建立后源 IP 恒定，代理不会中途换

`internal/proxy/socks5/server.go` 与 `internal/proxy/httpproxy/httpproxy.go` 的 CONNECT 路径都是：**Pick 一次 → Dial 一次 → 之后只做字节搬运**。没有任何重选、重拨、故障切换逻辑。

```go
entry, err := s.Picker.Pick("tcp", target)          // 只此一次
upstream, err := s.Dialer.DialContext(ctx, "tcp", target, entry)
...
pipe(local, upstream)                               // 直到结束
```

而且代理侧**不登记任何连接**（`metrics` 只计数，不留句柄），所以健康分变化、认证状态变化都不会关闭已建立的连接。健康检查里唯一的 `conn.Close()` 是探测自己的连接，不是用户流量。

结论：**在连接存活期间，源 IP 不可能「被换掉」**。所谓「换了 IP」，要么是物理地址真的变了，要么是另一条新连接选了别的 IP。

### 1.2 4 条连接并行下载，内容正确

见上表。HTTP 代理与 SOCKS5 两条路径都通过，四片拼接与单流下载逐字节相同。测试用的是真实网络（清华 TUNA 的 3.6 GB ISO 取前 20 MiB），不是本地 mock。

### 1.3 同一个 IP 上，并行不加速 —— 这正是「锚定 IP」的证据

4 条连接时每片约 1.4 MB/s，合计 5.63 MB/s；同样走代理的单连接是 5.74 MB/s。**连接数翻 4 倍，总吞吐反而略低（0.98 倍，差异在噪声内）。**

这说明限速的计量对象是源 IP，不是连接数 —— 与 Phase 0 得出的 `ip_anchored` 一致。反过来说，这也正是多 IP 能叠加的原因：每多一个 IP，就多一份独立的额度。

> 当时的外推（未实测，只有单个源 IP）：2 个 IP × 4 连接，每片仍约 1.4 MB/s，合计约 11–12 MB/s。
> 这个外推后来用第二块网卡验证过了，结果见 [`dual-path.md`](dual-path.md)：**叠加成立，但只有 1.39×**，瓶颈是两块网卡连在同一台 AP。

## 2. 被证伪的推论

「连接不能迁移」→「不能并行」，中间少了一步：

```text
错误推论：一条连接要跨多个 IP 才能聚合
实际情况：多条连接各占一个 IP，服务端看到的是多个客户端，带宽各自计算
```

TCP 的四元组固定，只约束**单条连接**；HTTP 的 `Range` 请求头允许**把一个文件切成多段、用多条连接分别取**。两者不冲突。

代码里也留了旁证（`internal/proxy/httpproxy/httpproxy.go` 明文转发计数那段）：Steam 走两个源 IP 实测到 94 Mbps，而面板当时显示 0。那是这条机制已经跑通的证据，只是当时被统计 bug 掩盖了。

## 3. 「断」的三种成因与判别方法

| 成因 | 现象 | 判别方法 | 对应修法 |
|---|---|---|---|
| **A. 明文 HTTP 逐请求换 IP** | 下载器并发多、进度条反复回退或 403；日志里同一目标连续出现不同 `source_ip` | 看 `caulinkd` 日志：同一 host 的相邻请求源 IP 是否不同 | 对下载目标固定 IP（粘性），或让下载器走 CONNECT/HTTPS |
| **B. 源 IP 真的失效**（DHCP 续租换地址、认证掉线、切网） | 所有连接同时 RST，任何下载器都断 | 断的瞬间 `ipconfig` 看地址是否变了；日志有无「IP 已变更」 | 分片 + 断点续传，单片重试而不是整个重下 |
| **C. 单流下载 + 站点对单 IP 限速** | 速度卡在 6 MB/s 上不去，看起来像「没生效」 | 用多连接测，速度是否随连接数变（同 IP 不会变） | 客户端侧分片，且必须跨 IP |

三者里只有 B 是「真的断了」，但 **B 和并行无关** —— 单流一样断，而且单流断一次要重下整个文件，分片只重下 5 MiB。换句话说，分片不只是提速手段，还是抗断手段。

A 是当时**真实存在**的行为：`handleForward` 为了简化，强制 `Connection: close`，每条明文 HTTP 请求都是新连接、新 Pick。对 Steam 的 CDN 分段下载这是优点（天然铺开），对签名 URL 就是缺点（IP 变了签名失效）。

## 4. 四个可选方案

| 方案 | 能否覆盖浏览器 | 开发量 | 合规 | 评价 |
|---|---|---:|---|---|
| **① 内建分片下载器** | 能（程序内下载，不受浏览器限制） | 中，约 700–900 行 + 测试 | 纯自研，无新增第三方 | **推荐**。唯一能对 HTTPS 做分片聚合的方案 |
| **② 集成 aria2 子进程** | 能（RPC 驱动） | 小，约 200–300 行 | GPLv2，需附许可证与源码获取方式 | 务实备选。成熟稳定，但无法保证「每片落在不同 IP」 |
| **③ 只给代理，用户自备下载器** | 不能（要用户装 IDM/aria2） | 零 | 无 | 现在就能用，但违背「一站式」 |
| **④ MITM 代理层分片** | 能 | 大 | **不可接受**：需自签 CA 解密 TLS | 否决 |

### 为什么必须在客户端分片

代理的 CONNECT 隧道里跑的是**已加密的 TLS 流**。代理看不到 HTTP 头，也就无法插入 `Range`、无法把一条下载拆成多段。想在代理层拆，只能解密 —— 那就是方案 ④，需要给用户装根证书，还要在校园网环境里解开别人的流量，合规上说不过去。

**所以「让浏览器下载也变快」这件事，只有两条路：程序自己做下载器，或用外部下载器。**

### 方案 ① 的最小实现要点

1. **能力探测**：先发 `Range: bytes=0-0`，看是否 `206` + `Content-Range` 里有总长。不支持就退化为单流，不要硬拆。
2. **一致性**：记录 `ETag` / `Last-Modified` / 总长度。所有分片必须带同一个 `If-Range`，最后一片返回的 ETag 与首片不一致就整单失败 —— 否则会拼出一个「前半段旧版、后半段新版」的坏文件，而且 md5 校验不出来（没有参照）。
3. **分片数**：`min(8, IP 数 × 2)`。分片数超过 IP 数的 2 倍没有意义，同一 IP 上的分片只会互相抢同一份额度。
4. **每片绑不同 IP**：`scheduler.Pick` 只表达「给我一个」，无法表达「给我一个不是我正在用的」。SWRR 本身会均匀分配，但一旦某个 IP 中途掉线，没有排除机制就容易两片挤到同一条线上。
5. **失败换 IP**：单片失败重试 3 次，每次排除上次用的条目；401/403 不重试（是权限问题，换 IP 更糟）。
6. **落盘**：`os.File.WriteAt` 并发写 + 预分配（`Truncate` 到总长），不要在多 goroutine 里拼内存再写 —— 4 GB 文件会直接把内存打爆。
7. **续传**：分片状态写 JSON（偏移、已完成字节、ETag），重启后继续。
8. **进度**：接到现有 `metrics` + `/api/v1/status`，UI 上显示总速度与每 IP 贡献。这是答辩时最有说服力的一屏。

工作量拆两期比较稳：第一期只做「单任务、固定分片、无续传」（约 400 行），能演示；第二期补队列、续传、限速。

> **后续**：方案 ① 的第一期已经落地在 `internal/accel`，实现与实测见 [`accel.md`](accel.md)。实际行数与上面估的接近（核心约 1200 行含测试）。

### 方案 ② 的具体命令（未实测）

打包 `aria2c.exe`，由 `caulinkd` 通过 JSON-RPC 驱动：

```text
aria2c --enable-rpc --rpc-listen-all=false ^
       --all-proxy=http://127.0.0.1:8080 ^
       --split=16 --max-connection-per-server=16 --min-split-size=1M ^
       --file-allocation=none -d <下载目录> <URL>
```

每条分片连接经过 HTTP 代理时各做一次 Pick，SWRR 会铺到不同 IP。**这条没实测**（本机没装 aria2），落地前要确认两件事：aria2 对 `Range` 与 `If-Range` 的处理是否满足上面第 2 条；GPLv2 的分发义务怎么在 `docs/compliance.md` 里写清。

## 5. 建议

1. **先纠正结论**，避免按错误前提砍掉功能。
2. **优先做方案 ① 的第一期**。它是唯一能真正实现「一站式加速」的路径，也不引入第三方二进制。
3. **顺手修 A 类问题**：给下载类目标加「同 host 粘性」，避免明文 HTTP 连续请求换 IP 把签名 URL 弄失效。这是一条分类规则的事（把下载站的 host 归到 `ClassInteractive`，或加一个 `ClassSticky`）。
4. **等第二个 IP 到位**，用同一份测试代码跑一次 2 IP × 4 连接，把 12 MB/s 这个外推变成实测。

---

## 6. 演示口径

单 IP 环境下，能证明的是**机制正确**（分片、校验、调度、故障隔离），不能证明**带宽叠加**。这两件事在答辩时必须分开讲。

不要为了让曲线好看去伪造多 IP 数据 —— 评委只要问一句「你这台机器有几个网口」，就会穿帮；而「机制已跑通、叠加幅度受拓扑限制」是个完全站得住的回答，尤其是当你能当场打开日志，指出四片分别走了哪条链路。
