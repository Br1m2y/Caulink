# Phase 0 · 限速锚点验证报告

> 结论：**限速锚定在 IP**。两个源 IP 并发总吞吐达到各 IP 单独测之和的 **100%**，
> 项目按「多 IP 聚合」主线推进。
>
> 原始数据：`tools/phase0/out/phase0-<运行戳>.json`（未入库，按约定只保存报告）
> 生成工具：`cmd/phase0probe`（同一份报告由工具自动产出，本文件补充了人工环境信息）

## 1. 结论与判据

| 指标 | 值 | 判据 |
|---|---|---|
| 各 IP 基线之和 | **12.19 MB/s** | —— |
| 最强单 IP 基线 | **6.10 MB/s** | 与"单接口约 6MB/s"的经验值吻合 |
| 并发总吞吐 | **12.17 MB/s** | —— |
| 并发 / 基线之和 | **1.00** | ≥ 0.80 判锚定 IP |
| 并发 / 最强单 IP | **2.00** | ≤ 1.35 判锚定账号 |
| 数据可信（基线过门槛） | **true** | 基线 ≥ 2.0 MB/s |

**判定：`ip_anchored`。** 每个源 IP 有独立配额，多 IP 可以线性叠加。

## 2. 实验环境

| 项 | 值 |
|---|---|
| 采集时段 | 闲时 |
| 主机 | LAPTOP-OLOB85H3 (windows/amd64, 20 核) |
| 链路 A | Intel Wi-Fi 6E AX211 · `10.6.18.3` · 5 GHz · ch 44 |
| 链路 B | AIC8800D80 USB WiFi · `10.6.53.173` · 5 GHz · ch 44 |
| 同一 AP | 是（BSSID `ec:da:59:0e:0c:c0`） |
| 采集地点 | 校园网无线，楼栋待补（TODO） |
| 测速目标 | `https://mirrors.tuna.tsinghua.edu.cn/...ubuntu-22.04.5-desktop-amd64.iso` |
| 每 IP 连接数 / 预热 / 测量 / 轮数 | 8 / 3 s / 15 s / 3 |
| 设备配额 | 2 个 IP，占账号 3 台配额中的 2 台 |

### 特别说明：两条链路共用同一 AP

两块网卡都连在同一个 AP、同一信道（44）。按空口共享原理，这本来可能压低并发结果，
**但实测并发仍然达到了 2.00 倍**，说明该 AP 在当前时刻有足够空口余量，
瓶颈确实在网关的**每 IP 配额**上，而不是无线链路。

反过来说：如果这次测得的是 1.0 倍，就无法区分"锚定账号"与"空口饱和"。
**这是本实验设计里最需要警惕的一处混淆**，所以报告中必须记录 AP/信道信息。

## 3. 逐 IP 单独测速（基线）

| 源 IP | 网卡 | 各轮 MB/s | 中位数 |
|---|---|---|---|
| 10.6.18.3 | WLAN | 6.10 / 5.56 / 6.11 | **6.10** |
| 10.6.53.173 | WLAN 2 | 6.09 / 6.06 / 6.11 | **6.09** |

两条链路的单 IP 上限几乎完全一致（6.09 vs 6.10），符合"每 IP 统一配额"的特征。

## 4. 全部 IP 并发测速

| 场景 | 各轮 MB/s | 中位数 |
|---|---|---|
| 2 个 IP × 8 连接 | 12.22 / 12.17 / 11.92 | **12.17** |

并发时各 IP 的实际贡献：

| 源 IP | 网卡 | 平均 MB/s | 连接数 |
|---|---|---|---|
| 10.6.18.3 | WLAN | 5.92 | 8 |
| 10.6.53.173 | WLAN 2 | 6.00 | 8 |

**两条链路各自仍然跑满 6MB/s**，说明它们互不挤占——这正是"独立配额"的直接证据。

## 5. 采集过程中的两次失败数据（方法论价值）

同一天做过三次采集，前两次都**判为无效**，记录下来是因为它们说明了两类典型陷阱：

| 时间 | 场景 | 结果 | 为何作废 |
|---|---|---|---|
| 19:14 | 机房，同楼层约 200 人上课 | 单 IP 1.00 / 0.65 MB/s，并发 1.20 | **晚高峰拥塞**，绝对吞吐只有闲时的 1/6，比值毫无意义 |
| 23:10 | 同上环境，USB 网卡认证过期 | 只有 1 个可用 IP | 网关把 HTTPS 劫持到 `*.cau.edu.cn` 证书，预检识别为不可用 |
| **23:16** | 同上环境，两 IP 均已认证 | **单 IP 6.10 / 6.09，并发 12.17** | ✅ 采用 |

由此得到两条必须写进操作规范的经验：

1. **必须在闲时测**（晚高峰数据会把"拥塞"误判成"账号限速"）；
2. **测速前逐个 IP 确认 `200`**（`302` 或证书报错都说明该 IP 未认证）。

## 6. 对项目的意义

| 结论 | 影响 |
|---|---|
| 多 IP 可线性叠加 | 「多 IP 聚合」主线成立，不必切换到"稳定性优化"叙事 |
| 单 IP ≈ 6 MB/s，双 IP ≈ 12 MB/s | README 中"多线程下载总吞吐可接近多 IP 之和"从假设变为实测 |
| 双 IP 占 2/3 设备配额 | 产品文案应强调"利用账号已有配额"，而不是"突破限制" |
| 单连接仍受 6 MB/s 限制 | 非目标第 1 条（不做单 TCP 聚合）必须继续贯彻 |

## 7. 复现步骤

```powershell
# 1) 两块网卡分别连校园网并各自完成 portal 认证
# 2) 逐个确认可达
foreach ($ip in @('<IP_A>','<IP_B>')) {
  curl.exe -s -o NUL -w "$ip -> %{http_code}`n" --interface $ip http://www.msftconnecttest.com/connecttest.txt
}

# 3) 预检 + 测速
netsh wlan show interfaces                      # 记录 AP/信道（写进报告）
phase0probe -config configs/phase0.example.json
```
