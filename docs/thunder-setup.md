# 迅雷下载走多 IP 调度

> 适用版本：`caulinkd`（SOCKS5 口一直存在，无需额外开关）。
> 相关：Steam 走的是 HTTP 代理，见 [`docs/steam-setup.md`](steam-setup.md)。

## 为什么迅雷比 Steam 简单

迅雷**原生支持 SOCKS5 代理**，所以直接填 `caulinkd` 已经开着的 SOCKS5 口就行，
不需要额外的 HTTP 代理：

```
迅雷 → SOCKS5(127.0.0.1:1080) → scheduler.Pick → dialer.Dial(绑定源 IP) → 下载源
```

## 前提条件（缺一不可）

| 前提 | 怎么确认 |
|---|---|
| `caulinkd` 已运行 | `GET http://127.0.0.1:7788/api/v1/status` 能返回 JSON |
| **至少两个**已认证的源 IP | 响应里 `ips[].schedulable` 至少两条为 `true` |
| Phase 0 已判定"限速锚定 IP" | 若锚定账号，多 IP 不会叠加带宽 |
| 两个 IP 不共用空口（建议，非必须） | 实测同 AP 同信道也能叠加，见下 |

实测：两块网卡连在**同一个 AP、同一信道（ch 44）**，
单 IP 各 6.10 / 6.09 MB/s，并发 **12.17 MB/s（2.00 倍）**。
也就是说空口并未成为瓶颈，**不需要为此调整频段**。只有在并发明显低于各 IP 之和时，
才优先改用有线链路。

## 步骤

### 1. 确认 SOCKS5 口在监听

默认配置里就有：

```json
"socks5": {
  "listen": "127.0.0.1:1080"
}
```

**只允许回环地址**，填 `0.0.0.0` 会被拒绝启动。

### 2. 启动 caulinkd

```powershell
caulinkd.exe -config configs/caulinkd.json -v
```

### 3. 先用 curl 自检，再去动迅雷

```powershell
curl.exe -x socks5h://127.0.0.1:1080 -s -o NUL -w "status=%{http_code}`n" https://www.baidu.com
```

`socks5h` 而不是 `socks5`：前者让 **DNS 解析也走代理**，更接近迅雷的实际行为，
也避免本机 DNS 污染干扰判断。

返回 `200` 才算代理正常。常见失败：

| 现象 | 含义 | 处理 |
|---|---|---|
| `502` / `curl: (56)` | 从选中的源 IP 建连失败 | 检查该 IP 是否真能上网 |
| `curl: (7)` | 连不上 SOCKS5 口 | `caulinkd` 没起，或端口不对 |
| 一直超时 | 没有可调度的 IP | 查 `/api/v1/status` 的 `auth_status` |

### 4. 在迅雷里配置代理

迅雷各版本位置略有差异，大致在两个地方之一：

```
迅雷 → 设置 → 基本设置 → 代理设置
   或  设置 → 网络/连接 → 代理

  ☑ 使用代理
  代理类型：SOCKS5
  地址：127.0.0.1
  端口：1080
  → 确定
```

> 迅雷的代理设置是**全局且持久**的：`caulinkd` 停止后迅雷会连不上网，见「用完记得取消」。

### 5. 验证流量确实分散到了多个 IP

开一个多线程下载任务，同时观察：

```powershell
while ($true) {
  curl.exe -s http://127.0.0.1:7788/api/v1/status |
    ConvertFrom-Json |
    ForEach-Object { $_.ips | Select-Object source_ip, auth_status, active_conns, rate_down_bps }
  Start-Sleep -Seconds 2
}
```

| 现象 | 说明 |
|---|---|
| 多个 `source_ip` 的 `active_conns` 都 > 0 | ✅ 连接分散成功，多线程任务会走不同源 IP |
| 只有一个 IP 有连接 | ⚠️ 另一个 IP 不可调度（认证掉 / 健康分为 0） |
| 都有连接但总速率≈单 IP | 见下一节 |

## 为什么可能不加速

| 原因 | 判断方法 |
|---|---|
| **限速锚定账号**（Phase 0 结论） | 单 IP 与多 IP 总吞吐几乎一样 |
| **任务只开了一条连接** | 迅雷"单线程下载"、或资源只支持单连接 |
| **BT 任务的部分流量绕过代理** | 见下方说明 |
| 两块网卡共用空口且 AP 已饱和 | 改用有线；同 AP 未必是问题，见上文实测 |
| 目标服务器限流 | 换个下载源试试 |
| 单连接场景 | 单个 TCP 连接的源 IP 固定，永远无法叠加 |

### 关于 BT / 磁力任务

迅雷对 **BT、磁力链接**的处理与普通 HTTP 下载不同：部分版本会对 P2P 连接做直连
（不经过代理），或者只把 tracker/HTTP 回源走代理。因此：

- **HTTP/HTTPS 直链下载**：代理生效最确定；
- **BT/磁力**：以实际观察到的 `active_conns` 分布为准，不要假设一定生效。

判断方法就是上面第 5 步——**看状态接口里连接是不是真的分散了**，而不是看任务管理器
的网卡占用。

## 用完记得取消

**`caulinkd` 停止后迅雷会无法联网**（它仍指向一个不存在的代理）。收尾二选一：

1. 迅雷 → 设置 → 代理设置 → **取消勾选"使用代理"**；
2. 或者保持 `caulinkd` 常驻运行。

## 已知边界

- **只影响走代理的连接**：迅雷自身的 P2P 直连、局域网传输不经代理；
- **单连接不加速**：这是项目的基本约束（见 README 的"技术栈"与非目标说明）；
- **不认代理的程序**需要 TUN 接管，目前未实现（看板 B10）。

## 与 Steam 的对照

| | 迅雷 | Steam |
|---|---|---|
| 协议 | SOCKS5 | HTTP |
| 端口 | `127.0.0.1:1080` | `127.0.0.1:8080` |
| 需要额外配置 | 不需要（默认就开） | 需要 `http_proxy.listen` |
| `caulinkd` 停了之后 | 迅雷断网，需手动取消 | Steam 断网，需手动取消 |
| 典型加速场景 | 多线程直链下载 | 游戏/更新下载（多分片连接） |
