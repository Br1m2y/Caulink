### 1.1 为什么 IP 池要提供两个窄接口

`ippool` 只有 `UpdateAuth` 和 `UpdateHealth`，没有"整条替换"。

这不是洁癖。认证层每 20 秒写一次 `auth_status`，健康检查每 10 秒写一次 `health_score`。如果两边都用"读整条 → 改自己那个字段 → 写整条"，那么在这两步之间对方写入的值必然被覆盖回去。症状是 `health_score` 周期性归零、调度权重乱跳，而且极难复现——取决于两个 goroutine 的调度时机。

窄接口把字段归属变成编译期就能看出来的约束：A 拿不到写健康字段的方法，B 也拿不到写认证字段的方法。

## 2. 关键决策一：平滑加权轮询，不是加权随机

`scheduler.pickSWRRLocked` 用的是 nginx 那套 smooth weighted round-robin：

```text
每个候选: current += weight
选中 current 最大者
被选中者: current -= 总权重
```

### 2.1 为什么不用加权随机

加权随机（按 `health/total` 的概率抽签）有两个问题：

1. **比例不准。** 100 次分配里，权重 50% 的两个 IP 可能一个拿 60 次一个拿 40 次。项目要演示"多 IP 分摊"，这种波动会让人怀疑调度根本没生效。
2. **可能连续命中同一个。** 短时间内的几个连接全压在一条链路上，那条链路先打满，而另一条闲着。总吞吐反而下降。

### 2.2 为什么不用普通加权轮询

普通加权轮询要把权重展开成固定序列（权重 5:1 就展开成 `A A A A A B`）。健康分是每秒都在变的浮点数，序列得不停重建，等价于每轮都重新算一次 SWRR，还要额外维护序列状态——多此一举。

SWRR 天然处理浮点权重、不需要序列、分配严格按比例。

### 2.3 权重下限 1 的坑

健康分 0.004 乘 100 取整是 0。权重 0 在 SWRR 里意味着**永远不被选中**，但它的 `HealthScore > 0` 又让 `Schedulable()` 认为它可用——形成"看得见、用不上"的僵尸条目。

所以 `weightOf` 里有 `if w < 1 { w = 1 }`。代价是极差链路会分到约 1% 的流量，这比"完全不用但又算在池子里"要诚实。

## 3. 关键决策二：健康分是连续函数，不是分段打分

```go
rttFactor = 1 / (1 + rttMs/200)
score     = (1 - lossRate) * rttFactor
```

- RTT 0ms → 1.0
- RTT 200ms → 0.5（每 200ms 权重减半）
- RTT 600ms → 0.25
- 丢包 100% → 0

### 3.1 为什么不用分段

分段打分（"RTT<50 给 1.0，50-100 给 0.8，>100 给 0.5"）在阈值边界会跳变。一条链路因为 1ms 的抖动从 0.8 掉到 0.5，SWRR 立刻把 37% 的流量挪走；下一秒又抖回来，流量再挪回去。整体表现为吞吐忽高忽低，很难解释。

连续函数没有这个问题，而且**一句话就能讲清楚**：RTT 每增加 200ms 权重减半。答辩时不需要画图。

### 3.2 为什么不用 ICMP

`health.dialRTT` 用 TCP 握手，不用 ICMP ping：

- ICMP 经常被校园网或目标防火墙屏蔽，拿到的全是丢包，等于没有数据。
- ICMP 的 RTT 与 TCP 建连时延不等价，而后者才是用户实际感知的东西。
- 裸 ICMP 需要 root，TCP 不需要。

## 4. 关键决策三：敏感流量带滞回，不是"永远选最优"

`pickStickyLocked` 的规则：

1. 敏感流量（UDP、游戏端口、会议域名）固定到当前最优 IP；
2. 下次同样流量来时，**只要当前绑定的 IP 健康分不低于最优的 80%，就继续用它**；
3. 低于 80% 或直接掉线，才换。

### 4.1 为什么必须有滞回

游戏和会议是长连接。换 IP 意味着**服务端看到一个全新会话**——游戏掉线重连、语音重新握手、会议中断几秒。

两条链路的健康分本来就小幅波动。没有滞回，谁高一点就往谁那边跳，一场语音会议可能被切断十几次。对这种流量，"稳"比"最优"重要一个数量级。

0.8 是经验值：低于这个比例说明当前链路已经明显劣化，继续坚持的代价大于切换的代价。

### 4.2 为什么会"粘"在一个次优 IP 上很久

极端情况：两个 IP 都是 0.9 和 0.72，永远不切换。这是设计意图，不是 bug。只要 0.72 那条还能用，就不值得为 25% 的质量提升中断一次会议。

### 4.3 端口分类的局限，要主动说明

默认规则靠端口判断（3478 是 STUN、27015-27030 是 Source 引擎等）。问题是**大量会议软件最终走 443**，这时会被判成 bulk，不享受粘性。

不打算用 DPI 或 SNI 嗅探来"解决"这个问题：那是另一个量级的复杂度，还会引入隐私争议。正确做法是在演示和文档里说明"端口规则覆盖常见场景，不是全知全能"，而不是假装它很准。

## 5. 关键决策四：拨号失败绝不回退

`dialer.DialContext` 在绑定源 IP 失败时直接返回错误，**不会**退回不绑源地址的默认拨号。

一旦回退，所有流量静默回到默认路由——多 IP 调度形同虚设，而现象只是"程序在跑、速度上不去"。这种降级比直接报错恶劣得多，因为它让失败看起来像正常。

正确做法：报错 → 调度层换一个 IP 重试 → 池里没有可用 IP 就明确告诉用户。

## 6. 与认证层的交界

**`guardian` 的在线检测请求必须绕过 TUN。** 这条写在《认证层设计.md》§8，这里重述是因为它是 B 的责任：

```text
TUN 接管全部流量 → guardian 的检测请求被 TUN 捕获
→ TUN 走代理 → 代理按 IP 池状态选路
→ 而 IP 池状态正等这次检测结果
→ 死循环 / 误判
```

更隐蔽的一种：代理把检测请求送到另一个已认证的 IP 上，guardian 看到"能连通"，判定在线，而这张网卡的认证其实早就掉了。

**B 在做 TUN 路由规则时，必须为 `internal/auth` 启的子进程留直连白名单**（建议按 cgroup 排除）。

### 7.1 SOCKS5 的接入方式

```go
// 收到 CONNECT 请求后：
entry, err := sched.Pick("tcp", target)
if err != nil { /* 回复 0x03 网络不可达 */ }
conn, err := dialer.DialContext(ctx, "tcp", target, entry)
// 然后双向转发，两端都正确 CloseWrite
```

已在 `internal/proxy/socks5` 实现。三个细节值得记下来：

1. **`ListenAddr` 强制校验回环。** 写死校验而不是靠文档约定——对外监听等于把已认证的校园网会话分享给整个网络，这是合规红线，不该留成配置项。
2. **半关闭必须显式做。** 只用两条 `io.Copy` 而不 `CloseWrite`，HTTP/1.0 那种"服务端先关"的协议会一直悬着，连接不释放。
3. **握手阶段必须有 deadline。** 端口扫描和半开连接很常见，没有超时的 handler 会被这些连接永久占住 goroutine。

### 7.2 UDP ASSOCIATE：比 TCP 难在"回程往哪送"

TCP 有连接句柄，回程天然知道往哪写。UDP 没有：服务端只有一个 socket，收到任何包都得自己判断它属于哪个客户端、哪个目标。这就是 UDP 关联的全部难点。

实现上的四个决定：

**1. 每个 `(客户端, 目标)` 组合一个已连接的 UDP socket。**

已连接的 socket 只收到该目标的包，省掉按来源过滤这一层；回程地址直接从 `RemoteAddr()` 拿。代价是每个目标占一个本地端口，所以必须配上限（512）和空闲回收（60 秒）——一个开了 HTTP/3 的浏览器半分钟就能开几十个会话。

超限时**丢弃新会话而不是淘汰最旧的**。淘汰旧会话会打断正在进行的游戏或会议，丢一个新包只是让那条新流慢一拍。

**2. 同一目标必须永远走同一个源 IP。**

这比 TCP 更硬。UDP 没有连接概念，游戏服务器靠 `(源 IP, 源端口)` 认玩家；中途换 IP 在服务端看来就是老玩家掉线、新玩家上线。会话表天然提供了这个粘性——会话活着就不重新 Pick。

**3. 源 IP 掉线时不静默换线。**

和 dialer 那条"绝不回退默认路由"是同一个原则。换线会让服务端看到新会话，同时掩盖了"这条链路已经不可用"的事实。让会话超时、由客户端下次发包时重新走 `Pick`，行为更可解释。

**4. `BND.ADDR/PORT` 必须回真实地址。**

这是 UDP 关联最容易写错的一处。CONNECT 的响应里 BND 填零值无所谓，客户端不看；但 UDP 的 BND 就是客户端要发包的目的地，回 `0.0.0.0:0` 意味着客户端把包发到一个不存在的地方，现象是"UDP 完全不通"而日志里一切正常。

顺带一个必须处理的平台差异：Windows 上对刚发出 ICMP 端口不可达的目标读，会返回 `WSAECONNRESET`。UDP 无连接，这一条不代表会话结束，容忍若干次连续错误而不是一遇错就拆会话。

### 7.3 TUN 的位置

TUN 只是把流量"喂"给同一个 `Pick` + `Dial` 流程，调度逻辑不需要改。这也是把 dialer 单独拆出来的原因：SOCKS5 和 TUN 都复用它。

### 7.4 指标与状态接口：C 的数据源

`ippool` 回答"这条链路**怎么样**"（认证状态、健康分），`metrics` 回答"这条链路**干了多少活**"（字节、连接数）。前者由探测驱动，后者由数据面驱动，更新者和失效条件都不同。

**合进 `ippool` 会毁掉那个刻意收窄的写入接口。** 一旦 `ippool` 里出现"累计字节"这种高频写入字段，`UpdateAuth` / `UpdateHealth` 的字段归属约束就守不住了，A 和 B 迟早会把对方的统计覆盖掉。所以宁可多一个包。

四个实现决定：

**1. 速率用 EWMA，不用瞬时差分。** 原始差分每秒采样，一个请求结束就能让曲线从 5MB/s 掉到 0，UI 上根本没法看。α=0.3 对应约 3 个采样周期的反应时间。代价是数字有滞后，但对"这条链路现在快不快"这个判断足够。

**2. 速率按真实 dt 算，不用标称间隔。** 调度延迟和 GC 停顿会让实际的采样间隔偏离 1 秒，用标称值会在系统繁忙时系统性高估速率。

**3. 计数按写入侧，不按读取侧。** 读到的字节可能多于实际交付的（对端发完就关），而 UI 想看的是"真正流过多少"。代价是包一层后 `io.Copy` 用不上 `net.TCPConn` 的 `ReadFrom`（Linux 上是 splice）。在这个场景不值得为此绕路：SOCKS5 每跳本来就是用户态拷贝，32KB 缓冲够跑满千兆。

**4. UDP 会话的计数挂在 `closeOnce` 上。** 会话可能被 `pumpInbound`、`janitor`、`shutdown` 三条路径同时关掉，只有 `sync.Once` 能保证"每条会话恰好减一次"。放错位置的后果是活跃连接数缓慢漂移到负数或者永久虚高，而且两种症状都极难复现。

状态接口本身只读、只监听回环。理由是**一个能改状态的本地接口等于给任何本机进程开了绕开调度的后门**。UI 改配置就改文件后重启。

一个容易忽略的序列化细节：空池必须输出 `"ips": []` 而不是 `null`。前端遍历 null 会直接抛异常，而空数组只是渲染一张空表。这个用 `make([]T, 0, n)` 而不是 `var s []T` 就能保证，测试里也锁住了。

字段契约见 [`docs/status-api.md`](../status-api.md)。

## 8. 已知局限（演示时要主动说）

1. **单条 TCP 连接不可能跨多个 IP。** 源地址在连接期内固定，这是 TCP 语义决定的。多 IP 只在"多条并发连接"时带来吞吐叠加。任何声称能加速单连接的方案都是错的。
2. **端口分类覆盖不到走 443 的会议流量。**
3. **健康分只反映到探测目标的链路质量**，不等于到任意目标的质量。目标在中国的镜像和在美国的服务器，最优 IP 可能不同。
4. **UDP 的域名解析不走调度。** 客户端把域名交给代理后，代理用系统 DNS 解析，这一步不经过源 IP 绑定。DNS 包小且少，影响可忽略，但严格说这部分流量没被分摊。
5. **UDP 关联不支持分片**（RFC 1928 允许）。FRAG 非 0 的报文直接丢弃，真实客户端几乎不用这个字段。
6. **状态接口不存历史，也不按目标聚合。** 只有当前值，重启即清零。要曲线得客户端自己滚动缓存；"哪个网站走了哪条线"这种按目标的分布没有，因为那需要在数据面按目标建表，开销与收益不成比例。
7. **回环地址测不出多 IP 差异。** 集成测试只能验证"链路通"，验证"多 IP 叠加"必须用 Phase 0 的真实环境。
