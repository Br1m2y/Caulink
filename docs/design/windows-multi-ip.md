# Windows 上做多 IP：可行性核查

> 起因：项目主线依赖"同一台机器上多个源 IP"。当前没有 Linux 机器，问 Windows 的虚拟 IP 功能能否替代。
> 结论在下一节，后面是依据。

---

## 1. 结论

**Windows 上的"虚拟 IP"不能替代多张物理网卡做这个项目的核心实验。** 不是配置问题，是三条独立的硬限制叠在一起：

1. 多 IP 的价值在认证层，而认证层的网卡绑定在 Windows 上不可靠（上游 README 明写）；
2. 唯一可能成立的"同网卡多 IP"方案需要向交换机冒用未分配地址，有 IP 冲突与违规风险；
3. 本机只有一张 Wi-Fi（Intel AX211），没有有线口，虚拟化桥接这条路也堵了。

**可以做的**：单 IP 跑通全链路（已实现，见 §6）。**不能做的**：验证"多 IP 吞吐叠加"这条主线。

---

## 2. 四种"虚拟 IP"，能力完全不同

| 方案 | 能不能发出去 | 能不能收到回包 | 对本项目有用吗 |
|---|---|---|---|
| 网卡辅助 IP（高级 TCP/IP 设置里加） | 能 | 要看交换机策略 | 唯一有可能，但风险高，见 §3 |
| Microsoft KM-TEST 环回适配器 | **不能** | 不能 | 无用。它只能访问本机，出不了网 |
| Hyper-V 外部虚拟交换机 | 能 | 能 | 家庭版没有 Hyper-V，且不能桥接 Wi-Fi |
| VirtualBox / VMware 桥接 | 能 | 能 | 每台 VM 只能一个 MAC 关联，多网卡不可行 |

最容易误解的是环回适配器——它确实能"生成一个 IP"，但那个 IP 只在本机协议栈内可见，任何发往外部网络的包都会被直接丢弃。用它测出来的"多 IP"是假的。

---

## 3. 辅助 IP：唯一有可能，但有两个硬风险

原理上说得通：给 WLAN 再加一个同网段的 IPv4 地址，绑源 IP 发包，网关收到目的地址是它的包会发 ARP，本机回 ARP（地址确实在本机），于是回包能通。

但有两道关，都不在我们控制范围内：

**风险一：交换机可能直接丢弃。** 校园网普遍在接入交换机上启用 DHCP Snooping + IP Source Guard，只允许 DHCP 分配过的 `MAC-IP` 组合通过。辅助 IP 是手工配的，不在 DHCP 租约里，这类配置下会被静默丢弃——现象是"能发包、收不到回包"，很难查。

**风险二：IP 冲突会伤到别人。** 手工挑一个"看起来空闲"的地址，如果它已经在 DHCP 池里分给了别人，两边同时在线会互相打断，对方直接断网。`10.6.0.0/17` 有三万多个地址，撞上的概率不高，但一旦撞上影响的是别人。

**还有一层：这可能违反学校的网络使用规定。** 未经分配使用一个 IP，性质上和私接路由器不同，但确实不属于"正常接入"。项目自己要求合规，这条得由你们判断。

**如果要测，成本最低的做法**（改完配置必须立刻还原）：

```powershell
# 1) 先确认目标地址没人用
ping -n 2 10.6.100.200

# 2) 加辅助 IP（需要管理员权限）
New-NetIPAddress -InterfaceAlias WLAN -IPAddress 10.6.100.200 -PrefixLength 17

# 3) 试能不能出网
ping -n 2 223.5.5.5
curl.exe -s -o NUL -w "%{http_code}" --interface 10.6.100.200 --max-time 8 https://mirrors.tuna.tsinghua.edu.cn/

# 4) 不管成功失败，立刻删掉
Remove-NetIPAddress -InterfaceAlias WLAN -IPAddress 10.6.100.200 -Confirm:$false
```

第 3 步的 `--interface` 能不生效是关键判据。如果只有第 2 步成功、第 3 步不通，说明被交换机拦了，别继续试别的地址。

> 我不建议由我在这台机器上直接执行这段——它会改网络配置，中途失败可能让你断网，而且第 1 步的 ping 不通并不等于地址真的没人用（对方可能开着防火墙）。

## 4. 这台机器的实际情况

```text
系统      Windows 11 家庭版 10.0.26200
网卡      WLAN  Intel Wi-Fi 6E AX211（10.6.92.171 / 17）
          Radmin VPN（26.208.129.115，虚拟网络，非校园网）
          蓝牙网络连接（未连接）
有线口    无
```

三条限制由此确定：

- **家庭版没有 Hyper-V**（需要专业版/企业版/教育版）。系统里 `HypervisorPresent=True` 是 WSL2/VBS 在用虚拟化平台，不等于 Hyper-V 管理功能可用。
- **即使有 Hyper-V，也不能桥接 Wi-Fi。** 微软的 Hyper-V 外部虚拟交换机只支持有线适配器，绑定无线网卡后该网卡会失去连接。
- **没有有线口，虚拟化桥接无处可桥。**

关于 Radmin VPN 那张网卡：它拿到的是 `26.208.129.115`，属于 Radmin 自建的虚拟局域网，只有同样装了 Radmin 并加入同一网络的设备能互通。它连不到校园网，也连不到公网，不能当作第二个源 IP。

## 5. 三条可行路径

| 路径 | 成本 | 能得到什么 | 限制 |
|---|---|---|---|
| **A. USB 有线网卡 + 有线接入** | 30–60 元 | 第二个物理接口 | 两个接口若在同一子网，仍需接口级绑定，Windows 上不可靠，见下 |
| **B. 一台 Linux 机器（旧笔记本/双系统）** | 0（如果有旧机器） | 完整能力：真认证 + 多 IP | 需要两个网络接口（Windows 亦可，见 ADR 0004） |
| **C. 只做单 IP 演示** | 0 | SOCKS5 接管、调度、粘性、健康检查全部可展示 | 展示不了"多 IP 叠加"，主线论证缺实测数据 |

**A 有个坑值得先说清楚。** 买 USB 网卡后，Wi-Fi 和 USB 有线大概率落在同一个 `/17` 网段。两个接口同网段时，光绑源 IP 不够——路由表会挑一个出口，可能挑错。Linux 上有 `SO_BINDTODEVICE` 能强制走指定接口，Windows 上要 `IP_UNICAST_IF`，Go 标准库不直接暴露，得自己 syscall。这正是 `认证层设计.md` §12 第 1 项要实测的内容。

所以 A 的性价比低于看起来的样子：钱花了，可能还得处理绑定问题。

**B 是最稳的**，因为 Linux 上 `SO_BINDTODEVICE` 和 `--interface` 都是现成的，上游项目也只在 Linux 上验证过。

## 6. 现在能做什么

单 IP 环境下，下面这些已经实现并且在本机实测通过：

| 能力 | 状态 | 怎么演示 |
|---|---|---|
| SOCKS5 接管浏览器/下载器 | ✅ 已实测 | `curl -x socks5h://127.0.0.1:1080` |
| TCP 连接按调度选路 | ✅ 已实测 | `-v` 日志看 `source_ip` |
| UDP 转发（QUIC / 游戏 / DNS） | ✅ 已实测 | DNS 查询往返，RTT 7ms |
| 健康探测与降级 | ✅ 已实现 | 拔网线看 `health_score` 变化 |
| 多 IP 加权轮询 | ✅ 有单测，❌ 无真实数据 | 集成测试能验证比例，但不是真实链路 |

**演示时该怎么说**：单 IP 环境下能证明"接管与调度机制正确"，证明不了"多 IP 吞吐叠加"。这两件事必须分开讲，把后者说成已验证会在答辩追问时塌掉。

---

## 7. 建议的推进顺序

1. 先用现有条件把功能补完（TUN 或 UDP 优化），不阻塞；
2. 同时解决硬件：优先找一台旧笔记本装 Linux，其次买 USB 网卡；
3. 硬件到位后跑 `Phase0验证方案.md`，拿到真实的聚合比数据；
4. `Phase0验证方案.md` §3.1 要求的"两个独立源 IP"，不要在 Windows 上硬凑——凑出来的数据不可信，比没有数据更糟。
