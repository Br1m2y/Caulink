# Phase 0 验证方案：限速锚点实验

> 对应《要求.md》§2 决策门、§4 Phase 0。这是整个项目**第一个必须先做完的事** ——
> 结论决定后面做「多 IP 聚合」还是「冗余稳定性」，两条路的工作量完全不同。
> 落地位置：`cmd/phase0probe/`、`configs/phase0.example.json`、`tools/phase0/`、`docs/reports/`。

---

## 1. 这个实验要回答什么

一句话：**学校的 6MB/s 限速，是限在"每个 IP"上，还是限在"每个账号"上？**

- 如果限在 **IP**：2 个 IP 各跑 6MB/s，一共能跑 12MB/s。多 IP 聚合有意义，项目按主线走。
- 如果限在 **账号**：2 个 IP 加起来还是 6MB/s。多 IP 白忙，项目要转向"冗余、切换、静默重认证"。

这个答案不能靠猜，也不能靠"别人说"，必须自己测出来。测错的代价是整个项目方向错。

---

## 2. 判定原理

分两个场景测，比较三个数字：

```text
场景 A（基线）：一次只让 1 个 IP 跑，逐个测完
场景 B（并发）：所有 IP 同时跑

sum   = IP1 单独测 + IP2 单独测        ← 各 IP 独立配额的"理论总带宽"
max   = max(IP1 单独测, IP2 单独测)     ← 单个 IP 的天花板
conc  = 所有 IP 同时跑的总吞吐
```

| 现象 | 含义 | 结论 |
|---|---|---|
| `conc ≈ sum` | 每个 IP 各有独立配额，互不挤占 | **限速锚定在 IP** |
| `conc ≈ max` | 多个 IP 共享同一份配额 | **限速锚定在账号** |
| 介于两者之间 | 部分共享，或测量受干扰 | **不确定**，重跑 |

工具内部用的判据：

- `conc / sum >= 0.80` → `ip_anchored`
- `conc / max <= 1.35` → `account_anchored`
- 其余 → `inconclusive`

阈值写在 `verdict.go` 顶部，改动必须同步改本文和报告模板。

### 2.1 为什么必须"每个 IP 用相同连接数"

基线是「1 个 IP × 8 连接」，并发是「2 个 IP × 8 连接」。单个 IP 承受的负载一样，所以两组数字可比。

如果基线用 8 连接、并发用 16 连接，那就分不清"带宽叠加"和"连接数变多带来的提升"了。

### 2.2 为什么要预热

TCP 慢启动会让前 1–3 秒的速率明显偏低。不丢掉预热期，测出来的平均速率会系统性偏低 20%–40%，看起来像"限速比 6MB/s 更低"，直接误导结论。

工具默认预热 3 秒、测量 15 秒，共 3 轮取中位数。

## 3. 前置条件

### 3.1 硬件（这一条最容易卡住）

**你需要两个能同时从校园网拿到独立 IP 的接口。**

一台笔记本通常只有一个 WiFi 或一个网口，插上就只有一个 IP。常见的凑法：

- 笔记本自带的 WiFi + 有线网口，同时连校园网（有些学校允许，有些不允许多拨）
- 买一个 USB 千兆网卡（几十块钱），和自带网口各插一根线
- 两个 USB 网卡

**没有两个 IP，这个实验做不了。**先解决硬件，别急着跑脚本。

### 3.2 软件

- ~~Linux 环境。~~ 已澄清：Phase 0 探针只做下载测速、绑本地 IP，Windows 原生支持；认证器用 `net.Dialer{LocalAddr}` 绑定源 IP，Windows 实测可用。不再是前置条件。多 IP 认证大概率失败。
- 两个 IP **都已认证成功**。工具只负责测速，不负责认证。
- 测速期间别开别的下载、别开视频、别开代理。

### 3.3 先手动认证两个 IP

工具不会帮你认证。先各自认证，确认能上网：

```bash
# 网卡 1
./caulink-auth --config auth-eth0.json --once
# 网卡 2（另开一个终端）
./caulink-auth --config auth-eth1.json --once
```

各自看到登录成功、能 `curl` 出公网内容，再往下走。

## 4. 操作步骤

### 4.1 编译

在仓库根（Linux 上直接编）：

```bash
go build -trimpath -o bin/phase0probe ./cmd/phase0probe
```

在 Windows 上交叉编译到 Linux：

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o bin/phase0probe-linux ./cmd/phase0probe
```

### 4.2 先跑预检（不测速）

```bash
./bin/phase0probe -dry-run
```

输出示例：

```text
== 阶段一：枚举本机源 IPv4 ==
  192.168.1.23 (eth0)
  192.168.1.88 (eth1)
共 2 个候选源地址

== 阶段二：连通性预检 ==
选定测速目标: https://mirrors.tuna.tsinghua.edu.cn/...

  [可用  ] 192.168.1.23  eth0  HTTP 200 可正常访问
  [可用  ] 192.168.1.88  eth1  HTTP 200 可正常访问

2 个源 IP 通过预检
```

**必须看到 2 个「可用」。** 如果某个 IP 显示"不可用"，先解决它，别继续跑：
- `未认证` → 这个 IP 的认证没成功
- `链路不通` → 网卡没连上，或没路由
- `目标异常` → 换测速目标，见 §7

### 4.3 正式测速

```bash
./bin/phase0probe -config configs/phase0.example.json
```

大约需要 `(warmup + duration) × (IP 数 + 1) × rounds` 秒。默认参数下 2 个 IP 约 3.5 分钟。

结果写在 `tools/phase0/out/`：
- `phase0-<时间>.json` —— 原始数据，所有数字都能追溯到这里
- `phase0-<时间>.md` —— 自动生成的报告，补完 TODO 就能交

## 5. 参数说明

| 参数 | 默认 | 说明 |
|---|---|---|
| `targets` | 清华 / 中科大 / Cloudflare | 工具会挑一个"通过预检的 IP 最多"的目标。不按顺序取第一个，因为第一个可能已经失效 |
| `connections_per_ip` | 8 | 每个 IP 的并发 TCP 数。低于 4 条跑不满带宽，高于 16 条对结果提升有限 |
| `duration_seconds` | 15 | 稳态测量时长。太短误差大 |
| `warmup_seconds` | 3 | 预热，丢弃。**不要设为 0** |
| `rounds` | 3 | 每个场景重复几轮，取中位数 |
| `cooldown_seconds` | 5 | 轮次间隔，让服务器侧限速状态恢复 |
| `exclude_interfaces` | 见配置 | 排除虚拟网卡。**VPN 网卡一定要排除**，见 §7 |

命令行可以覆盖配置：

```bash
./bin/phase0probe -conns 12 -duration 20 -rounds 5
./bin/phase0probe -target "https://your-own-speedtest-file"
```

## 6. 结果解读

### 6.1 正常结果

```text
== 结论 ==
限速锚定在 IP。多 IP 并发可实现吞吐叠加（并发 11.82 MB/s vs 单 IP 最高 6.05 MB/s），
项目可按「多 IP 聚合」主线推进。
  - 并发总吞吐 11.82 MB/s，达到各 IP 单独测之和 12.10 MB/s 的 98%，说明每个 IP 有独立配额。
```

→ 走主线，进 Phase 1。

### 6.2 反例

```text
限速锚定在账号。多 IP 无法叠加带宽（并发 6.12 MB/s，仅单 IP 的 1.01 倍），
项目应转向「多链路冗余与稳定性优化」主线。
```

→ 立刻切换叙事，别硬撑。这不算失败，反而是最有价值的结论：省下了做无用功的几周。

### 6.3 不确定的三种原因

| 报告里的提示 | 真实原因 | 怎么办 |
|---|---|---|
| 单 IP 基线低于 0.5 MB/s | 测速目标太慢，或出口本身不行 | 换目标，或换时段重跑 |
| 并发在两者之间 | 并发连接数不够，或测量时长太短 | `-conns 12 -duration 20` 重跑 |
| 各 IP 基线差距超过 3 倍 | 某个 IP 链路本身差 | 单独查那张网卡，或只用好的那两个 |

## 7. 实测踩过的坑（都是真事，别重踩）

### 7.1 VPN 虚拟网卡会拖慢整个实验

本机同时开着 Radmin VPN，枚举出一个 `26.208.129.115` 的虚拟网卡。预检时它超时 8 秒，什么都没测出来，白等。

工具默认已经排除常见 VPN / 容器网卡（`radmin`、`zerotier`、`tailscale`、`docker`、`veth` 等）。如果你用别的 VPN，把名字加进 `exclude_interfaces`。

**排查信号**：枚举出的 IP 数量比你实际连的网口多。

### 7.2 伪装浏览器 UA 会被镜像站拦成 403

这个反直觉，但实测如此：

| UA | 清华 TUNA |
|---|---|
| 伪装 Chrome | **403** |
| 不发 UA | **403** |
| Go 默认 `Go-http-client/1.1` | **403** |
| `caulink-phase0probe/0.1.0` | 200 |

镜像站的防盗链逻辑是"冒充浏览器但 header 不全 → 拦"。工具已经改成自己的 UA，不要改回去。

### 7.3 Cloudflare 的测速端点有体积上限

`speed.cloudflare.com/__down?bytes=200000000` 直接 403，`bytes=50000000` 才正常。默认配置已经改成 5000 万字节。

如果将来这个也失效，换成本地镜像站的 ISO：`https://mirrors.<你的学校或公司>.edu.cn/...`。

### 7.4 "所有 3xx 都是认证页"是错的

最初版本把 302 一律判为"校园网劫持"，结果镜像站正常跳转（ISO 被移到归档路径）被误判成"未认证"。工具现在只在**同时满足**三个条件时才判劫持：

1. 重定向到了不同主机
2. 响应是 HTML
3. body 以 `<` 开头

三个都满足才是认证页。宁可放过也不误杀——误判成"未认证"会让人白折腾账号。

## 8. 合规边界

- 只用**本人授权账号和设备**。不要拿别人的账号测。
- 测速流量走公网镜像，不针对学校任何服务器。
- 并发连接数控制在 8 到 16 条，不要拉到几百条去打学校出口。
- 测完把两个 IP 的认证子进程停掉，别长期挂着占设备额度（农大限 3 台）。

## 9. 报告怎么写

工具已经生成 `tools/phase0/out/phase0-<时间>.md`，直接补 5 个 TODO：

1. 账号与设备情况（几个账号、几台设备在线）
2. 单接口标称 6MB/s 与实测的对比
3. **多 IP 同时认证是否导致其他设备掉线**（这条最关键，见《认证层设计.md》§12 第 5 项）
4. 异常记录
5. 三人签字确认

补完另存为 `docs/reports/phase0-限速锚点验证.md`，提交 PR。

这份报告是 Phase 1 的入场券，也是答辩时"我们验证过"的证据。
