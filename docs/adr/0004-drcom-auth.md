# ADR 0004 · 认证协议从深澜（Srun）改为 Dr.COM ePortal

- 状态：已采纳
- 影响范围：`internal/auth`、`cmd/caulink-auth`、`cmd/caulinkd` 的 auth 配置、
  `docs/design/auth-layer.md`、`third_party/`、合规叙事
- 取代：ADR 之前关于「用 BitSrunLoginGo 做认证」的全部假设

## 背景与发现

项目早期按"深澜（Srun）校园网"设计认证层，选型 `BitSrunLoginGo`（AGPL-3.0，
独立子进程调用）。做认证真机联调时，直接抓取农大 portal 页面发现：

```
<!--Dr.COMWebLoginID_1.htm-->                        ← Dr.COM 的页面标记
authloginport=801
authloginpath='/eportal/?c=ACSetting&a=Login'
authuserfield='DDDDD'  authpassfield='upass'
authlogoutpath='/eportal/?c=ACSetting&a=Logout&ver=1.0'
charset='gb2312'
```

**农大用的是 Dr.COM（城市热点），不是深澜。** `BitSrunLoginGo` 只支持 Srun 协议，
在这个网络上一行都跑不通。

## 决策

自己实现 Dr.COM ePortal 客户端 `cmd/caulink-auth`，保持"每源 IP 一个子进程"的
既有架构（`internal/auth` 的 supervisor/worker/probe 全部复用）。

## 实测协议（可复现）

### 登录

```
POST http://10.3.191.9:801/eportal/?c=ACSetting&a=Login
Content-Type: application/x-www-form-urlencoded

DDDDD=<学号>@cau&upass=<密码>&R1=0&R2=&R3=0&R6=0&para=00&0MKKey=123456
```

- 成功 → `302` 到 `.../3.htm?...`
- 失败 → `302` 到 `.../2.htm?...RetCode=<原因>`
- **不需要验证码**（网页表单有验证码，但这条 API 路径不走它）

### 注销

```
GET http://10.3.191.9:801/eportal/?c=ACSetting&a=Logout&wlanuserip=<IP>
→ 302 到 .../2.htm?...ACLogOut=1
```

### 在线判定

从绑定的源 IP 请求 `http://www.msftconnecttest.com/connecttest.txt`：

- `200` 且内容含 `Microsoft Connect Test` → 在线
- `302` / 连接失败 → 离线

## 三个必须踩过的坑

| 坑 | 表现 | 修正 |
|---|---|---|
| **账号缺 realm** | RADIUS 返回 `no AT symbol in realm`，登录失败但 HTTP 200 | 账号拼成 `<学号>@cau` |
| **探测跟随重定向** | 302 到登录页后被 Go 自动跟随，拿到登录页的 200 → 误判"在线"，重认证永不触发 | 探测客户端设 `CheckRedirect: http.ErrUseLastResponse`，且校验响应内容 |
| **源 IP 不绑定** | 登录请求从默认路由出去，认证的是另一台设备 | `net.Dialer{LocalAddr: <source_ip>}` |

第二个坑最隐蔽：表现是"子进程活着、状态一直是 reauthenticating、但永不重登"。

## 真机验证记录

```
00:05:05  用 API 注销 10.6.53.173（模拟断连）→ 探测变 302
00:05:45  守护进程探测到重定向 → 状态 online → reauthenticating
00:06:06  子进程检测到离线 → 调用登录 → 成功
00:06:30  守护进程探测回 200 → 状态 reauthenticating → online
```

**全程无人干预，49 秒内自动恢复。**

### 恢复延迟的调优

49 秒里慢的不是登录（登录本身 < 1s），而是**轮询间隔**：`guardian_seconds` 当时是 60。

调整后：

| 项 | 之前 | 现在 |
|---|---|---|
| 子进程检查周期 | 60 s | **10 s**（带 0–2 s 抖动，避免多 IP 同步探测） |
| 守护进程探测周期 | 20 s | **10 s** |
| 实测恢复时间 | 49 s | **8.0 / 5.1 / 6.3 s**（三次） |

单次探测约 0.6 s、几百字节，10 秒一次的开销可以忽略（每 IP 约 8600 次/天）。
再往下压到 5 秒收益递减，且会让门户和探测目标承受不必要的请求——10 秒是
"恢复快"与"请求量"的平衡点。

> 注意：最坏情况仍是一个周期（约 12 秒）。要做到"秒级以下"，需要事件驱动
> （例如由代理层观察到上游失败时立刻通知认证器），目前未实现。

## 事件驱动重认证

轮询模式的天花板是"最坏要等一个检查周期"。既然产品本来就在持续建连，就让
**观察者直接触发重认证**，轮询退回兜底（30s）。

### 三个观察点，按可靠性排序

| 观察点 | 能发现什么 | 实测 |
|---|---|---|
| **应用层探测**（internal/auth） | 门户劫持：请求被 302 到 `10.3.x.x` | **主力路径**，检测→恢复约 **0.5–1.3s** |
| **代理层建连失败**（internal/proxy/dialer） | 丢包式断网（SYN 被丢弃/超时） | 真实存在但**本网络少见** |
| 认证子进程轮询（30s） | 以上都漏掉的情况 | 兜底 |

### 为什么建连失败不是主力信号

实测确认：**未认证时门户在网络层拦截 TCP，建连是成功的**，只是应用层被重定向到登录页。

```
未认证时：curl --interface <离线IP> http://任意站点  → TCP 连接建立成功 → 302 到门户
```

所以"连接失败"在这张网里几乎不会出现，代理层看不到异常；HTTPS 更是连响应都看不见。
只有主动发一个 HTTP 探测，才能识破"TCP 通、但流量被劫持"这个状态。

建连失败的回调仍然保留：如果学校改成丢包式断网（或网卡/驱动异常），它就是最快的那条路径。

### 探测节奏：自适应，而不是固定高频

固定 2 秒探测的代价是每 IP 每天约 4 万次请求。虽然只有几百字节，但对"挂着不用"的用户
是白花的钱。真实需求是不对称的：

| 场景 | 用户感受 | 合适的节奏 |
|---|---|---|
| 正在下载/游戏 | 断线立刻有感 | **2s**，此时探测相对几 MB/s 的流量占比万分之一 |
| 空闲挂着 | 根本不知道 | **30s**，省下的请求不会影响任何人 |

所以探测周期由**当前是否有流量**决定（`auth.Options.ActivityFunc`，数据来自
`internal/metrics` 的实时速率与连接数）：

```
有流量（连接数>0 或 速率>32KB/s）→ 2s
空闲                              → 30s
```

切换会打一条 DEBUG 日志，便于确认自适应生效：

```
00:48:49 探测切换到快速模式（有流量） id="WLAN 2@... " interval=2s
00:49:06 探测切换到省流模式（空闲）   id="WLAN 2@... " interval=30s
```

**最坏恢复时间**（真实断连，无模拟延迟）：

| 状态 | 检测 | 登录 | 合计 |
|---|---|---|---|
| 有流量 | ≤2s | 0.3–0.5s | **≤2.5s** |
| 空闲 | ≤30s | 0.3–0.5s | ≤30.5s |

> 早期实测里的"端到端 6 秒"包含了一段**模拟假象**：测试是调门户的注销接口断开的，
> 而门户要 ~2.3 秒才真正停止放行流量。真实断连（网卡掉线、会话被踢）没有这段延迟。

### 实测

```
00:28:47.905  门户劫持被探测到 → reauthenticating
00:28:48.433  事件驱动重认证成功 → online          ← 528ms
00:28:55.837  → 00:28:57.120                        ← 1.28s
```

端到端（从注销到恢复）约 **6 秒**，其中：

- 门户实际断流延迟 ≈ 2.3s（不可控）
- 探测等待 ≤ 2s（可调，但收益递减）
- 登录本身 ≈ 0.3–0.5s

### 防抖

一次掉线会伴随成串触发信号（每个失败连接、每次探测）。三层保护：

1. 代理层回调只做非阻塞入队，攒够 3 次失败/5s 才举手（`internal/reauth`）；
2. 重认证前**再探测一次**确认，避免目标站点故障导致误登录；
3. 每个实例 3s 冷却 + 单飞标志，同一时刻只有一个登录在飞。
## 后果

**正面**

- 真正能登录农大校园网了（此前完全不可用）；
- **不再依赖 AGPL-3.0 的第三方二进制**，`third_party/bitsrunlogin-go.exe` 可以删除，
  合规叙事从"进程隔离"简化为"无第三方认证代码"；
- 协议自主可控，出现异常时能直接改代码而不是等上游。

**负面**

- 认证协议成为自维护代码：学校升级 portal 时需要跟进；
- 密码在局域网里明文传输（Dr.COM 门户本身是 HTTP），这是协议固有问题，与实现无关。

## 保留的兼容性

`internal/auth` 的子进程契约没变（`--config <path> --interface <nic>`），
换认证器只需要改 `auth.binary` 指向 `bin/caulink-auth.exe`。
生成的实例配置从 bitsrun 的 `Config.yaml` 改成 `auth.json`（字段见
`docs/design/auth-layer.md`）。

## 若学校更换认证系统

判断顺序：

1. 抓 portal 页面，看有没有 `Dr.COMWebLoginID` / `srun_portal` 之类标记；
2. 若有 `srun` 特征，可回到 `BitSrunLoginGo`（子进程契约不变，换二进制即可）；
3. 若是其他厂商，按同样方式先抓登录请求，再实现 `cmd/caulink-auth` 的对应协议。
