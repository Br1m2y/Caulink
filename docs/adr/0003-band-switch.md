# ADR 0003 · 主网卡频段切换（已放弃）

- 状态：**已放弃**（立项当天即放弃）
- 影响范围：原本计划新增 `internal/bandswitch`、`internal/winlaunch` 与
  `bandswitch-*` 命令行入口
- 结论：**功能已从代码库移除**。本文件保留决策过程，避免以后有人重新踩一遍。

## 当时的设想

校园网 `CAU` 只广播一个 SSID，Windows 会把两块网卡都送上信号最好的 5GHz 射频。
若两块网卡连在同一 AP、同一信道，空口时间共享，多 IP 就叠加不了带宽。
于是设想：检测到这种冲突后，**把主网卡（Intel）切到 2.4GHz**，
另一块留在 5GHz，实现频段分离。

实现方案（已完成过一轮，后被移除）：

- 写 `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4d12...}\<网卡>\RoamingPreferredBandType`；
- 重启网卡生效（断流 10–20 秒）；
- 三层恢复保险：异常退出恢复、正常退出还原、`-bandswitch-revert` 手动兜底；
- 用 `ShellExecuteW "runas"` 做按需提权（方案 B，避免 GUI 常驻管理员）。

## 为什么放弃

**Phase 0 实测给出了反证：**

| 场景 | 结果 |
|---|---|
| 两块网卡**连在同一 AP、同一信道（ch 44）** | 单 IP 6.10 / 6.09 MB/s，**并发 12.17 MB/s（2.00 倍）** |

也就是说：**即使共用同一段空口，多 IP 依然完整叠加。**

原因是那个 AP 的空口容量（当时约 300 Mbps 链路）远大于两条链路各 6 MB/s 的需求，
空口并不是瓶颈；真正的瓶颈在网关的**每 IP 配额**上。

于是这个功能的收益变成了 **0**，而代价一条没少：

| 代价 | 说明 |
|---|---|
| 断流 | 切换要重启网卡，10–20 秒无法上网 |
| 提权 | 改 HKLM 必须管理员，GUI 要按需 UAC |
| 崩溃残留 | 异常退出后网卡可能一直停在 2.4GHz |
| 2.4GHz 更差 | 该频段干扰多，单链路速率可能低于 5GHz |
| 依赖 | 需要引入第三方依赖 `golang.org/x/sys` 读写注册表 |

**结论：为一个收益为零、代价明确的系统级改动保留代码，不值。** 全部移除。

## 移除清单

| 项 | 处理 |
|---|---|
| `internal/bandswitch` | 删除 |
| `internal/winlaunch` | 删除（唯一用途就是本功能的提权） |
| `cmd/caulinkd` 的 `-bandswitch-*` | 删除 |
| `internal/control` 的 `band_switch` 段 | 删除 |
| `configs` 的 `band_switch` 字段 | 删除 |
| `golang.org/x/sys` 依赖 | 移除，项目回到零依赖 |

## 如果将来确实需要频段分离

先回答一个问题：**空口真的是瓶颈吗？** 判断方法：

1. 跑 Phase 0：若并发吞吐接近各 IP 之和（≥0.8），空口不是瓶颈，**不要做**；
2. 若并发明显低于单 IP 之和，先排除目标服务器与晚高峰（见
   [`docs/reports/phase0.md`](../reports/phase0.md) 的两条作废数据）；
3. 仍然偏低时，**优先让用户改用有线**，而不是改驱动参数；
4. 万不得已才考虑频段分离，且优先给**第二块网卡**加频段限制，
   而不是动主网卡（主网卡一动，用户的网络就断了）。

## 保留的替代能力

- 有线 + 无线：物理上不共享空口，最优解；
- 状态接口里的链路信息足以让 UI 提示用户"两块卡在同一 AP"（若将来需要，
  可以只做**检测 + 提示**，不做自动修改）。
